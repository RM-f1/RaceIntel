## 3. Evaluation Methodology

### Verification Standard
Every ground truth answer is traceable to:
1. **SQLite Database** (`data/raceintel.db`): Verified records from `events`, `drivers`, `constructors`, `race_results`, `laps`, and `weather_observations`.
2. **ChromaDB Production Knowledge Base** (`data/chroma`, 503 documents): Verified reports generated by `RaceDocumentGenerator`.
3. **Deterministic Ground Truths**: Non-hallucinatory refusal standards for unanswerable and ambiguous questions.

### Answer Comparison Logic
- **Structured Answers (`dict`)**: Driver name matching, uppercase finishing position equality (`P1`–`P20`), and floating-point numerical tolerance ($\le 0.001$).
- **Numerical Answers (`float`/`int`)**: Extracted numerical values matched against ground truth with a tolerance of $\pm 0.05$.
- **List Answers (`list[str]`)**: Full set membership verification ensuring all expected items are represented.
- **Unanswerable Questions**: Verification that actual responses contain standard refusal markers (*"couldn't find that information"*, *"not available"*) and do **not** fabricate a driver, position, points, or winner.
- **Ambiguous Questions**: Verification that responses identify ambiguity or request query clarification.

### Dual Execution Modes
`evaluation/run_evaluation.py` supports:
1. **Live HTTP Mode**: Sends queries via `requests.post()` to `http://127.0.0.1:8000/chat/`.
2. **In-Process Mode (`--in-process`)**: Uses FastAPI's `TestClient(app)` to run evaluations deterministically, reproducibly, and offline without requiring a separate server process.

## 6. Incorrect Answers Analysis

The 12 failed evaluation cases fall into three distinct architectural categories:

### A. Missing ChromaDB Knowledge Indexing (8 cases)
* **Cases 58–63 (Weather)**: Questions regarding rainfall and temperatures (e.g., *"Did it rain during the 2024 Canadian Grand Prix?"*, *"What was the average air temperature during the 2024 Bahrain Grand Prix?"*).
  * *Root Cause*: Weather data is richly populated in SQLite (`weather_observations`, 3,690 rows) and available via REST endpoint `/weather/{session_id}`, but is not compiled into text documents within ChromaDB.
* **Cases 48, 49 (Standings & Lap Time)**: Questions on championship standings and fastest lap pace.
  * *Root Cause*: Standings and lap times reside in SQLite (`race_results`, `laps`) and `/standings/` / `/pace/` REST endpoints, but the ChatService RAG pipeline relies exclusively on ChromaDB `race_report` and `driver_report`.

### B. Chat Routing & Semantic Disambiguation (2 cases)
* **Case 50 (Fastest Lap in British GP)**: Expected `Carlos Sainz`.
  * *Root Cause*: Although `Fastest Lap: Carlos Sainz` exists in the British GP `race_report` text in ChromaDB, `ChatService._direct_answer()` lacks a regex handler for "fastest lap" or "lap time", causing it to fall through.
* **Case 57 (Constructor Points Leader in Bahrain)**: Expected `Red Bull Racing`.
  * *Root Cause*: ChatService pattern matching matched the "most points" regex, but evaluated individual driver reports instead of constructor standings, answering `Max Verstappen` instead of `Red Bull Racing`.

### C. Retrieval Robustness / Semantic Leakage (2 cases)
* **Case 64 (2024 Indianapolis 500)**: Expected `UNANSWERABLE`.
  * *Root Cause*: "Indianapolis 500" is not in the F1 calendar. ChromaDB filter extraction found no race name and fell through to semantic search, which returned Hungarian GP reports. The "who won" direct answer regex then answered with Hungarian GP winner `Oscar Piastri`.
* **Case 67 ("Who won the race?")**: Expected `AMBIGUOUS`.
  * *Root Cause*: Unqualified query fell through to unconstrained semantic search, returning the top match (Emilia Romagna GP winner `Max Verstappen`).

| Out-of-Scope Season (`2022 Canadian Grand Prix`) | Refuse / State unanswerable | Retrieved empty context; refused | **PASS** |

| Unspecified Race (`Who won the race?`) | Request clarification | Semantic fallback hallucinated Imola GP | **FAIL** |

**Finding**: When the retriever extracts an explicit season filter outside 2024 (e.g., 2023, 2022), ChromaDB returns an empty context, and the system correctly refuses to hallucinate. However, when an unanswerable question lacks recognized entities altogether, unconstrained semantic retrieval can surface unrelated races.

## 9. System Limitations Identified

1. **RAG Knowledge Base Partitioning**:
   - ChromaDB holds 503 documents covering race summaries and driver race classifications.
   - High-granularity data in SQLite (3,690 weather rows, 26,604 lap records, championship standings) is isolated in REST endpoints and absent from the vector knowledge base.
2. **Semantic Fallback Without Confidence Gating**:
   - If a query mentions an unknown event (e.g., Indianapolis 500), the retriever falls back to unconstrained semantic similarity and returns top-5 unrelated documents.
3. **ChatService Direct Answer Limitations**:
   - `ChatService._direct_answer()` has no handlers for fastest lap times, weather conditions, or championship standings.

---

## 10. Recommendations for Phase 3

1. **Knowledge Base Ingestion Expansion**:
   - Index session weather summaries as `weather_report` documents in ChromaDB.
   - Index post-race championship standings as `standings_report` documents in ChromaDB.
2. **Retrieval Confidence Thresholding**:
   - Introduce a maximum cosine distance threshold (e.g., distance $\le 0.4$) on ChromaDB semantic queries. Queries falling below the threshold should return empty context rather than irrelevant races.
3. **Guardrails for Out-of-Domain & Ambiguous Queries**:
   - Check whether a detected query refers to a known race, driver, constructor, or session before triggering direct answering templates.
4. **Execute Live RAGAS Scoring**:
   - Once user approval is granted, execute `run_ragas_evaluation.py --pilot-size 8` to compute genuine empirical faithfulness, context precision, context recall, and answer relevancy scores.
